# BOX FE tests — where to look

`[2026-10-13]` One page for the three FE tests (`box-fe-technical-test`, `box-fe-y-test`, `box-fe-parallel-test`), so
no run has to search for a table again. Written after the NY_SCH technical test (DGBOUS, 24/09/2026, two ALCO
deposits): the agent could not find the counterparty table, and an import that selected nothing ended OK. The SQL
is generated by `scripts/fe_test_sql.py` (shared by `fe_tech_test.py` and `fe_reconcile.py`).

## 1. Static data behind a RAW value

A RAW value (counterparty, folder, currency…) is matched by **alias** (`ALIASCODE`, owner object, extension, source —
[`box-fe-static-aliases.csv`](box-fe-static-aliases.csv)); the alias's `FK_PARENT` is the PK of the static row.

| Object | Static table | Status |
|---|---|---|
| Counterparty (alias owner `1448.4`) | **`PGT_STC.T_PGT_ENTITY_S`** | confirmed `[operator, 2026-10-13]`; also `sigom-metamodel.md` (`apCounterparty`) |
| Folder / portfolio mirror (`1453.4`) | **`PGT_STC.T_PGT_FOLDER_S`** — the alias code is the folder's `DESCRIPTION` (Murex name), not always its `CODE` (§6) | confirmed `[operator, 2026-10-23]` |
| Currency (`1382.4`) | `PGT_STC.T_PGT_CURRENCY_S` | INFERRED (`box-data-model.md`) |
| Any other | **find it**: `GOM_GLB_SYS.T__OBJ_DEF_S.BASIC_STORAGE` where `PK` = the alias's `FK_OWNER_OBJ` | rule (`sigom-metamodel.md` §2) |

```sql
SELECT PK, PK_NAME, BASIC_STORAGE, EXT_STORAGE FROM GOM_GLB_SYS.T__OBJ_DEF_S WHERE PK IN (1448.4, 1453.4, 1382.4);
```

`[operator, 2026-10-23]` 2629.65 resolves only the source-system alias: a missing folder alias does not stop the import
(the deal and flow rows are there); the trade gets no financial status. Check the aliases **before** the run (§6).

`<CODE>` is the **product** code, not the menu label: Depo `MM`, Swap `IR`, C&F `CF`, CCS, OTC, CFM, FRA, FX, CES,
CDS, BRS ([`sigom-reference.md`](sigom-reference.md)).

**Lesson — "the process didn't fail but there was no data."** An import that selects nothing ends OK. After each key
step the test checks the rows for **every** trade; 0 rows is a failure, diagnosed before the next step.

## 3. Why a step wrote nothing — group → event → procedure → its filters

```
group  PGT_PRC.T_PGT_BR_EVE_S
  └ events  PGT_PRC.T_PGT_BR_EVE_EXT_S (EVENTCODE, ORDERTOEXECUTE) → PGT_PRC.T_PGT_EVE_S
      └ Update / Calculate tab  PGT_PRC.T_PGT_UPDATE_S.TXFUNCNAME = <owner>.<package>.<procedure>
          └ the cursor  ALL_SOURCE (OWNER, NAME = package, TYPE 'PACKAGE BODY'): its WHERE lines
```

`sql/70-…-diagnose.sql` returns the events, the procedures and every line of those packages that filters
(`INSTRUMENT`, `BOOK`, `SOURCESYSTEM`, dates, `DATA_EXECUTION_TYPE`, status, branch). Compare them with the RAW rows:
the first mismatch is the root cause.

**Lesson — the INSTRUMENT text.** `BOX_FE.PKG_…p_Import_Mtm_Data` selects `mtm.INSTRUMENT = 'Loan / Depos'`; the NY
RAW market data rows carried `INSTRUMENT = 'Deposit'` → nothing imported, no error `[operator, 2026-10-13]`. Every
test checks the INSTRUMENT text of each RAW table for the trades against the text the procedures expect
(`p_Import_Deal_Data`'s list: `Loan / Depos`, `IRS`, `Commodity Swap`, `Currency Swap`, `CDS`, `CFM`, `FRA`, `OTC`,
`Cap and Floor`, `Bond Return Swap`, `Commodity Physical`). A mismatch is a Data Lake / RAW mapping finding for the
BOX team, not something the test fixes.

## 4. GBO vs BOX for the same trades

**The product codes differ between the two systems** `[operator's SIGOM menu lists, 2026-10-13]`. The full list, with
every GBO product (including those BOX does not have) and every BOX product, is
[`gbo-box-product-tables.csv`](gbo-box-product-tables.csv); the scripts read it (`fe_test_sql.py`).

| BOX product (code) | GBO product(s) (code) | Financial data: GBO → BOX |
|---|---|---|
| Depo (`MM`) | LoanDeposit (`MM`) — **compared, confirmed** | `DEVENG.T_PGT_MMFINANCST_S` → `BOX_FE.T_BOX_MMFINANCST_S` |
| Swap (`IR`) | Swap (`IR`) | `T_PGT_IRFINANCST_S` → `T_BOX_IRFINANCST_S` |
| CCS (`CCS`) | **CS (Currency Swap) (`SW`)** | `T_PGT_SWFINANCST_S` → `T_BOX_CCSFINANCST_S` |
| C&F (`CF`) | Cap & Floor (`CF`) | `T_PGT_CFFINANCST_S` → `T_BOX_CFFINANCST_S` |
| CFM (`CFM`) | CFM (**`IF`**) | `T_PGT_IFFINANCST_S` → `T_BOX_CFMFINANCST_S` |
| CDS (`CDS`) | Credit Derivatives (**`CD`**) | `T_PGT_CDFINANCST_S` → `T_BOX_CDSFINANCST_S` |
| FRA (`FRA`) | FRAS (**`FR`**) | `T_PGT_FRFINANCST_S` → `T_BOX_FRAFINANCST_S` |
| OTC (`OTC`) | **five**: OTC > OB, OE, OF, OI, OS | `T_PGT_O?FINANCST_S` (5 tables) → `T_BOX_OTCFINANCST_S` |
| FX (`FX`, not live) | **four**: FX Spot `SP`, FX ND Spot `NDS`, FX Fwd swap points `FP`, money market `FM` | 4 tables → `T_BOX_FXFINANCST_S` |
| CES, BRS | none in the GBO list — OPEN | — |

Pairings other than MM are INFERRED from the menu names: confirm each with its first comparison. A BOX product made of
several GBO products gets one GBO query per GBO table, read together. Deal data: GBO one table per product
(`T_PGT_<code>DATAMIS_S`), BOX one shared table `BOX_FE.T_BOX_DATADEAL_S` (every product's Deal Data menu is a view
on it). MtM: GBO `T_PGT_<code>RISK_S` (the FX products share `T_PGT_FXRISK_S`), BOX the view
`V_BOX_ENG<code>DATAMIS_S`. GBO-only Financial Status products (equities, ETD, futures, lending, repo, SCF …) have no
BOX table.

| | GBO (PROD) | BOX (DEV / PRE Paralelo) |
|---|---|---|
| Financial data | `DEVENG.T_PGT_<GBO code>FINANCST_S` by `DEAL_ID`, `DDATE` (MM confirmed) | `BOX_FE.T_BOX_<BOX code>FINANCST_S` by `DEAL_ID`, `DDATE` (MM confirmed) |
| The common key | `FRONT_ID`, through `DEVENG.T_PGT_<GBO code>DATAMIS_S` (GBO's `DEAL_ID` differs from BOX's) | `FRONT_ID`, through `BOX_FE.T_BOX_DEAL_DATA_S` |

```sql
-- GBO (operator's query, 2026-10-13)
SELECT * FROM DEVENG.T_PGT_MMFINANCST_S WHERE DEAL_ID IN (SELECT DISTINCT DEAL_ID FROM DEVENG.T_PGT_MMDATAMIS_S
WHERE FRONT_ID IN (<FRONT_IDs>)) AND DDATE = DATE '<date>';
-- BOX
SELECT * FROM BOX_FE.T_BOX_MMFINANCST_S WHERE DEAL_ID IN (<BOX DEAL_IDs>) AND DDATE = DATE '<date>';
```

The generated queries add `FRONT_ID` to both outputs (join to the deal table), so `fe_reconcile.py files … --key
FRONT_ID` compares them column by column. The field map [`gbo-box-fe-field-map.csv`](gbo-box-fe-field-map.csv) is
generated from the product list (financial data first).

## 6. The folder alias — what the NY IRS test taught `[operator, 2026-10-23]`

DGBOUS, IRS: every step ended OK, the trades got no financial status. Cause: the RAW `FOLDER` had no folder alias
for source `279.4` (GER, the one `c_Deal` reads) — the folder had one for another source only.

| Fact | |
|---|---|
| Folders | `PGT_STC.T_PGT_FOLDER_S` (`PK`, `FK_OWNER_OBJ` 1453.4, `FK_PARENT`, `FK_EXTENSION`, `CODE`, `DESCRIPTION`, `FK_BRANCH`, `FK_BUSINESSORG`, `FK_GLOBALPROD`, `FK_COVERAGETYPE`, `COVERAGEIND`, `FK_COVERAGELIST`) |
| The alias code | the folder's `DESCRIPTION` (its Murex name) — not always its `CODE` |
| Aliases | `PGT_TRD.T_PGT_OBJ_SOURCE_S` (`PK`, `FK_OWNER_OBJ`, `FK_PARENT`, `FK_EXTENSION`, `ALIASCODE`, `FK_SOURCE`); folder: owner `1453.4`, extension `10513.4` |
| Unique keys | `UN_PGT_OBJ_SOURCE_S_001` (`FK_PARENT`, `FK_OWNER_OBJ`, `FK_EXTENSION`, `FK_SOURCE`): **one alias per folder and source** · `UN_PGT_OBJ_SOURCE_S_002` (`FK_OWNER_OBJ`, `FK_SOURCE`, `ALIASCODE`): **one folder per code and source** |
| A new alias's PK | `PGT_TRD.PKG_SIGOM_COV.P_SETHEADER(STRTABLENAME IN, PK_VALUE IN OUT, FK_OWNER_VALUE IN OUT)` — both OUT arguments are overwritten: reset them before **each** call; check the PK returned is unused before the insert |

**Before the run** — `sql/30` (folder alias pre-check): per trade, the target branch's folders whose `DESCRIPTION` or
`CODE` is the RAW `FOLDER`, their `279.4` alias and their aliases for every source. `MISSING` → create the `279.4`
alias; `OTHER CODE` → the folder already has another `279.4` alias (`_001` blocks a second): ask the BOX FE team;
`CODE ON <pk>` → the code is another folder's `279.4` alias (`_002`): `c_Deal` finds that folder — check its branch.

**Creating it in DEV** (the operator runs it; no agent touches a database): check both unique keys first (an
`ORA-00001` on `_001` means the folder already has an alias for that source — insert only the missing source), get the
PK from `P_SETHEADER`, insert, then the pre-check again → `OK`. Then the re-run (§7).

## 7. Re-running the financial steps `[operator, 2026-10-23]`

Once **2608.65** Create Process Queues by Book BOX has run for a branch, instrument and date, the financial steps
cannot just be run again. From SIGOM's Run Batch screen:

1. **2815.65** ENG GN Main Back Dia Queue By Book BOX (the BACK group) — branch, instrument, label;
2. check in **BOX - Financial Engine › Process Management › Monitor**: Process Calendar "Generation of Financial
   Status", queues "Programmed Financial Status Generation";
3. **2608.65** again, then **2389.65** (per book).

The technical test's run card carries it (rows R1–R4). NY IRS in DGBOUS: folder alias created, then 2815.65 → 2608.65
→ 2389.65 gave the financial status.

## 8. Running a `db.conf` job by hand (Unix) `[operator, 2026-10-23]`

The job runner `db.sh` connects with the `ORACLE_CONNECT` of `GM_ENV` (DGBOUS: user `pgtadmin`), or a per-job profile
at `$GM_PROFILE_PATH/<job>` (or `/dynamic/<job>`) when one exists (none in DGBOUS), and compiles the call as that
user. A `PLS-00201` on `BOX_SYS.PKG_BOXUTILITY` in DGBOUS was a missing grant to that user: granted in DGBOUS; a
**DEV-only** case — it does not happen in PRE or PRO. See [`runs/_reference/tier2-pre/README.md`](../../runs/_reference/tier2-pre/README.md).
