# BOX — System Overview

**BOX (Back Office Express)** is the central back-office platform in the AUKI architecture at Santander. It receives trade details, cash flows and MtM data from Murex, runs financial calculations, and generates the accounting entries that feed into the bank's official books (the General Ledger).

## BOX Environments

BOX is installed in two different data-center environments, each one serving specific countries and branches where specific configs, local adaptations or logics can be configured.

**Tier 1** - BOX is installed in the Madrid machines. This Tier 1 environment physically located in Madrid hosts two branches: Madrid and SLB (London Branch).
**Tier 2** - BOX is installed in the US machines. This Tier 2 environment physically located in the US hosts the following branches: US, Brazil and Mexico.

## Technologies

- Back-end logic: PL/SQL - Oracle DB
- Front-end screens: Sigom is the front-end tool used to manage and configure the BOX system (backed by the Oracle DB tables).
- Data storage: Oracle DB
- Jobs: Control-M / Airflow / Lambda SQL

## From GBO to BOX

**Think of BOX as a pipeline:** A trade goes in at one end, and accounting records come out at the other.

BOX replaces **GBO** as the accounting source of truth. For each product migrated into the AUKI circuit, **BOX ACC** takes ownership of generating the **OBBs (accounting posting messages)** that were previously generated by GBO.

GBO is the previous system that generated accounting entries for the bank's official books (the General Ledger), and is very similar to BOX in terms of functionality and tables.

## Architecture Position

Both arrival paths (detailed in *Two Arrival Paths* below) converge into the same BOX stages — they just enter at different points, since the batch path never touches BOX_TRD:

```
REAL-TIME / ONLINE PATH
MUREX (Front Office)
    ↓
TIBCO EMS (Message Bus)
    ↓
Murex PBC (Integration Layer)
    ↓
CAMUNDA (Orchestration)
    ↓
BOX PBC (BOX Integration)
    ↓
   enters BOX at Stage 1: Trade Arrival

OVERNIGHT / BATCH (D+1) PATH — does not pass through BOX_TRD
MUREX (via Murex feeders)
    ↓
Data Lake (Lago)
    ↓
BOX Oracle RAW Tables (T_BOX_RAW_DEAL/FLOW/MARKET_DATA_S)
    ↓
   enters BOX at Stage 3: FE Calcs

┌──────────────────────────┐
│           BOX            │
│  Stage 1: Trade Arrival  │ ← online only
│  Stage 2: Validation     │ ← online only
│  Stage 3: FE Calcs       │ ← both paths converge here
│  Stage 4: ACC Generation │
│  Stage 5: MIC Dispatch   │
└──────────────────────────┘
    ↓
MIC (Pre-Ledger)
    ↓
AC&G (Madrid GL) / Equation (London branch SLB GL)
```

## Two Arrival Paths

### Real-time (Online) via API
- Trader books deal in Murex → trade arrives in BOX within seconds
- Path: Murex → TIBCO EMS → Murex PBC → Camunda → BOX PBC → BOX
- BOX_TRD consumes from product-specific Kafka topic
- Each product family has dedicated trade processor deployment and Kafka topic
- This path is for trade validation: checking that we have the accounting attributes needed (strategy, portfolio properties, ...) in order to produce the accounting entries for the incoming trade.

### Overnight (Batch – D+1) via the Data Lake (Lago)
- The purpose of this path is to receive the information needed to calculate and generate accounting for the trades
- Trade details, cash flows and MTM updates arrive in bulk from Data Lake (Lago)
- Path: Murex (via Murex feeders) → Data Lake (Lago) tables → BOX Oracle RAW Tables → BOX FE
- RAW tables in schema `BOX_FE`:
  - `T_BOX_RAW_DEAL_DATA_S` – deal structure
  - `T_BOX_RAW_FLOW_DATA_S` – cashflows
  - `T_BOX_RAW_MARKET_DATA_S` – market value

### Testing a branch that is already live in GBO `[stated: BOX Lead, 2026-09-10]`

The batch path can be driven by hand. A branch already live in GBO has its trades in the Data Lake
tables already, so they can be taken from there and loaded into the RAW tables directly — no trade needs
to be booked in Murex to run technical tests. Two caveats apply: the trade status will **not** be
`BOValidated` (that is the AUKI status), and the **online entry must be simulated**, because it is the
online path — not the batch path — that validates the accounting attributes (strategy, portfolio
properties) described above. Detail and the open decisions in `fe-raw-data-stage.md` (*Manual RAW feed
as a test path*) and `../examples/ny-sch-branch-onboarding.md` §2.

## Accounting Principle

**Accounting is by differences** – every Debit must equal every Credit:

```
Debit - Credit = 0
```

BOX never posts an unbalanced entry.
